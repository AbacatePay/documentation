<Tip>
  A **chave de API** é sua credencial de acesso à AbacatePay. Ela identifica sua conta e autoriza cada requisição enviada para a nossa API. **Sem uma chave válida, nenhum pedido será aceito.**
</Tip>

Toda requisição para a API da AbacatePay deve incluir sua chave no header `Authorization`. A chave também define o ambiente — uma chave de Dev mode simula transações, uma chave de Produção processa valores reais. Você não muda de URL para mudar de ambiente; muda a chave.

## O que você pode fazer com suas chaves

As chaves de API são gerenciadas diretamente pelo dashboard. Com elas, você pode:

- Ver todas as chaves ativas  
- Criar novas chaves para diferentes projetos  
- Revogar chaves comprometidas ou que não são mais usadas  

<Card title="Dev mode x Produção" horizontal>
  Todas as requisições usam o mesmo endpoint [api.abacatepay.com](https://api.abacatepay.com).  
  O ambiente é definido **pela chave utilizada**:
  - Chaves criadas em **Dev mode** → transações simuladas  
  - Chaves criadas em **Produção** → transações reais  

  Saiba mais sobre o ambiente de testes <a href="./devmode">aqui</a>.
</Card>

<Card title="Erro de Autenticação (401)" horizontal>
  Você receberá um **HTTP 401** quando:

  - A chave não for enviada no header  
  - A chave estiver incorreta  
  - A chave tiver sido revogada  
</Card>

## Permissões da chave de API

Além de identificar sua conta, a chave de API define **quais recursos** você pode acessar. Cada rota exige uma permissão; sem ela, a API responde **401** com o erro `Insufficient permissions`.

Ao criar a chave no dashboard, atribua só as permissões que a integração usa: por exemplo, uma chave só para ler clientes ou outra só para criar cobranças.

### Permissão de cada rota

| Permissão | Rotas |
| --------- | ----- |
| `CHECKOUT:CREATE` | `POST /checkouts/create`, `POST /payment-links/create` |
| `CHECKOUT:READ` | `GET /checkouts/get`, `GET /checkouts/list`, `GET /payment-links/get`, `GET /payment-links/list` |
| `CHECKOUT:DELETE` | `POST /checkouts/delete`, `POST /payment-links/delete` |
| `REFUND:CREATE` | `POST /checkouts/refund`, `POST /payment-links/refund`, `POST /transparents/refund` |
| `TRANSPARENT:CREATE` | `POST /transparents/create`, `POST /transparents/simulate-payment` |
| `TRANSPARENT:READ` | `GET /transparents/get`, `GET /transparents/list`, `GET /transparents/check` |
| `SUBSCRIPTION:CREATE` | `POST /subscriptions/create`, `POST /subscriptions/change-plan`, `POST /subscriptions/record-usage` |
| `SUBSCRIPTION:READ` | `GET /subscriptions/get`, `GET /subscriptions/list`, `GET /subscriptions/checkouts/get`, `GET /subscriptions/checkouts/list` |
| `SUBSCRIPTION:DELETE` | `POST /subscriptions/cancel`, `POST /subscriptions/checkouts/delete` |
| `CUSTOMER:CREATE` | `POST /customers/create` |
| `CUSTOMER:READ` | `GET /customers/get`, `GET /customers/list` |
| `CUSTOMER:DELETE` | `POST /customers/delete` |
| `PRODUCT:CREATE` | `POST /products/create` |
| `PRODUCT:READ` | `GET /products/get`, `GET /products/list` |
| `PRODUCT:DELETE` | `POST /products/delete` |
| `COUPON:CREATE` | `POST /coupons/create` |
| `COUPON:READ` | `GET /coupons/get`, `GET /coupons/list` |
| `COUPON:UPDATE` | `POST /coupons/toggle` |
| `COUPON:DELETE` | `POST /coupons/delete` |
| `WEBHOOK:CREATE` | `POST /webhooks/create` |
| `WEBHOOK:READ` | `GET /webhooks/get`, `GET /webhooks/list` |
| `WEBHOOK:DELETE` | `POST /webhooks/delete` |
| `WITHDRAW:CREATE` | `POST /payouts/create`, `POST /pix/send` |
| `WITHDRAW:READ` | `GET /payouts/get`, `GET /payouts/list`, `GET /pix/get`, `GET /pix/list` |
| `STORE:READ` | `GET /stores/get`, `GET /stores/list` e as rotas de [Public MRR](/pages/trustMRR/reference) (`/public-mrr/*`) |
| `BANK_STATEMENT:READ` | `GET /bank-statement/list` |

Cada endpoint da documentação indica qual permissão é necessária no topo da página.

## Troubleshooting

<AccordionGroup>
  <Accordion title="401 Unauthorized — o que verificar">
    Causas mais comuns, em ordem de frequência:

    1. O header `Authorization: Bearer SUA_CHAVE` não está sendo enviado
    2. A chave foi copiada com espaços extras ou caracteres invisíveis
    3. A chave foi revogada no dashboard
    4. Você está usando uma chave de Dev mode em uma URL que exige produção (ou vice-versa)
    5. A chave não tem a permissão da rota: nesse caso, o erro vem como `Insufficient permissions`

    Para confirmar que a chave está funcionando, teste diretamente:
    ```bash
    curl https://api.abacatepay.com/v2/stores/get \
      -H "Authorization: Bearer SUA_CHAVE"
    ```
  </Accordion>

  <Accordion title="Insufficient permissions — permissão ausente">
    A chave é válida, mas não tem a permissão da rota. Veja na [tabela de permissões](#permissão-de-cada-rota) qual permissão a rota exige e crie no dashboard uma chave nova com ela: não dá para mudar as permissões de uma chave que já existe.
  </Accordion>

  <Accordion title="Chave de Dev mode vs Produção — qual estou usando?">
    No dashboard, as chaves de Dev mode têm um indicador visual. Se você não tem certeza, verifique o campo `devMode` em qualquer resposta da API — `true` significa Dev mode, `false` significa Produção.
  </Accordion>
</AccordionGroup>

## Boas práticas de segurança

<Card horizontal>
  * Armazene suas chaves em variáveis de ambiente  
  * Nunca publique sua chave em repositórios ou grupos  
  * A AbacatePay **nunca** solicitará sua chave  
  * Revogue imediatamente qualquer chave que possa ter vazado  
</Card>

Depois disso, você já pode enviar requisições. O exemplo abaixo cria uma cobrança PIX de R$ 10,00 e exige uma chave com a permissão `TRANSPARENT:CREATE`:

```bash
curl -X POST https://api.abacatepay.com/v2/transparents/create \
  -H "Authorization: Bearer {{API_KEY}}" \
  -H "Content-Type: application/json" \
  --data '{
    "method": "PIX",
    "data": {
      "amount": 1000
    }
  }'
```

<Card title="Nota Importante">
  O mesmo endpoint [api.abacatepay.com](https://api.abacatepay.com) é usado para o ambiente de desenvolvimento e produção. O ambiente é determinado automaticamente pela chave de API utilizada na requisição.
</Card>
